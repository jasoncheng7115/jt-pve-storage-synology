jt-pve-storage-synology

A Proxmox VE storage plugin for Synology NAS over iSCSI. 透過 iSCSI 連接 Synology NAS 的 Proxmox VE 儲存 plugin。

One VM disk is one thin LUN on the NAS, so DSM's own snapshots, clones and capacity act on the unit an operator actually thinks about — no LVM layer, and no shared LUN carved up locally. 一顆 VM 磁碟就是 NAS 上一個精簡配置 LUN，所以 DSM 自己的快照、複本與容量都作用在操作者心裡想的那個單位上——沒有 LVM 夾層，也不把一個共用 LUN 在本機切開。

Status and risk狀態與風險

The plugin works, and it is still a prerelease.plugin 可以用了，而且它仍然是預發行版。 pvesm add synologysan works, and every lifecycle operation has been driven end to end against a DS918+ on DSM 7.1.1, twice, leaving nothing behind. The honest reasons it is still a prerelease: one node, one model, one DSM version, and no VM has booted from it yet. Five bugs surfaced in the first hour of running it that no amount of reading had shown — assume there are more. pvesm add synologysan 可以用了，而且每一個生命週期操作都已對一台 DS918+（DSM 7.1.1）完整跑過兩輪，沒有留下任何東西。它仍然是預發行版的誠實理由是：一個節點、一個機型、一個 DSM 版本，而且還沒有任何 VM 從它開機過。開始實際運行的第一個小時就冒出五個讀程式碼讀不出來的缺陷——請假設還有更多。

It is public at this stage for two reasons. The discovery tool is useful on its own to anyone who wants to know what their DSM's SAN API offers. And the register of what is and is not known about that API is worth reading before anyone trusts a plugin built on top of it — including this one. 在這個階段就公開有兩個理由。探索工具本身對任何想知道自己的 DSM 的 SAN API 提供什麼的人都有用；而那份「哪些知道、哪些不知道」的登記簿，值得在任何人信任一個建立在它上面的 plugin 之前先讀——包括信任這一個之前。

Why this is awkward麻煩在哪裡

Synology publishes no specification for the SAN Manager Web API. The only official document, the DSM Login Web API Guide, covers logging in and discovering APIs — and documents no LUN, target, mapping or snapshot call at all. Synology 沒有公開 SAN Manager Web API 的規格。唯一的官方文件 DSM Login Web API Guide 只涵蓋登入與 API 探索，完全沒有記載任何 LUN、target、對應或快照的呼叫。

What does exist is two independent implementations that talk to it in production: Synology's own CSI driver and OpenStack Cinder's Synology driver. This project's facts come from reading those two against each other, and then from asking real hardware. 真正存在的是兩份在生產環境和它對話的獨立實作：Synology 官方的 CSI driver 與 OpenStack Cinder 內建的 Synology driver。這個專案的事實來自把這兩份互相對讀，然後再去問實機。

That last step is not a formality. The two disagree, and where they disagree at least one of them is wrong on any given DSM. On the DSM 7.1.1 used for testing, Cinder's way of carrying a session fails every call, and on a NAS with anti-CSRF protection enabled — a default-available setting — neither client works at all, because neither sends the token DSM then requires. 最後那一步不是形式。兩份的做法有出入，而只要有出入，在任一台特定的 DSM 上至少有一份是錯的。在用來測試的 DSM 7.1.1 上，Cinder 帶工作階段的方式讓每一個呼叫都失敗；而在開啟防 CSRF 保護的 NAS 上（那是一個隨手可開的設定），兩份都完全不能用，因為兩份都沒有送 DSM 要求的那個 token。

Where nothing could be established, this plugin refuses the operation rather than guessing. A storage plugin that quietly guesses is worse than one that says no. 凡是無法確認的地方，這個 plugin 拒絕該操作，而不是猜。一個會默默猜測的 storage plugin 比一個會說不的更糟。

Only protocol facts are taken from those projects — API names, method names, parameters, error codes. No code is derived from either; this is Perl and its structure is its own. 從那兩個專案取用的只有協定事實——API 名稱、方法名稱、參數、錯誤碼。沒有任何程式碼衍生自它們；本專案是 Perl，結構是自己的。

A rule the kernel source would get wrong一條讀核心原始碼會讀錯的規則

A Synology LUN's WWID is built from its uuid: Synology LUN 的 WWID 是由它的 uuid 組成的： 

WWID = "3" + "6001405" + (uuid with "-" replaced by "d", first 25 characters)

6001405 is Linux-IO's IEEE company identifier, so the target is LIO-based — which is exactly the trap. Upstream LIO converts the serial with hex_to_bin() and skips every non-hex character, which would drop the hyphens and produce a different WWID entirely. Synology maps them to d. Reading the upstream source would have given a confidently wrong answer; only hardware gave the right one. 6001405 是 Linux-IO 的 IEEE 公司識別碼，所以 target 是 LIO 系的——而這正是陷阱。上游 LIO 用 hex_to_bin() 轉換序號，會跳過每一個非十六進位字元，那樣會把連字號丟掉，算出完全不同的 WWID。Synology 是把它們映射成 d。讀上游原始碼會得到一個很有自信的錯誤答案，只有實機給了對的。

The last 11 characters of the uuid are discarded, so the WWID cannot be inverted back to a uuid. The computed value is a cross-check; the kernel's own identification is what decides. uuid 的最後 11 個字元被丟掉了，所以 WWID 無法反推回 uuid。算出來的值是交叉核對用的，最終認定由核心自己的識別決定。

Rollback倒回

Neither reference implementation has a snapshot rollback: Kubernetes and Cinder both restore by cloning a snapshot into a new volume, so neither needed one. The method was found by asking a DSM about nine candidate names, one of which answered — restore_snapshot, taking src_lun_uuid and snapshot_uuid. 兩份參考實作都沒有快照倒回：Kubernetes 與 Cinder 都是用「把快照複製成一個新的 volume」來還原，所以兩者都不需要。這個方法是靠對一台 DSM 詢問九個候選名稱找到的，其中一個回答了——restore_snapshot，收 src_lun_uuid 與 snapshot_uuid。

Finding the name was not enough to enable it. Three things had to be true, and none was knowable in advance: 找到名稱還不足以把它打開。有三件事必須成立，而事先沒有一件是可知的：

The LUN's uuid must not changeLUN 的 uuid 不可以變 It does not. The SCSI serial and the WWID survive, so a node does not suddenly find a different disk where its own was它不會變。SCSI 序號與 WWID 都存活，節點不會突然在自己磁碟的位置上找到另一顆
Snapshots newer than the restored one must survive比還原點更新的快照必須存活 They do. Restoring to the oldest of three left all three in place會存活。還原到三個之中最舊的那一個，三個都還在
It must be observable afterwards事後必須看得出來 restored_time records the epoch second of the restorerestored_time 會記錄還原當下的 epoch 秒
The second row is why the related projects refuse a rollback past newer snapshots: on those arrays the newer ones are destroyed, so letting PVE do it silently would delete snapshots the user could still see. Here nothing is destroyed, so that restriction is not needed and a disk can be rolled back repeatedly. 第二列正是相關專案拒絕越過較新快照倒回的原因：在那些陣列上較新的快照會被銷毀，所以讓 PVE 默默做那件事，等於刪掉使用者還看得到的快照。這裡什麼都不會被銷毀，所以那道限制不需要，一顆磁碟也可以反覆倒回。

One VM disk is one LUN, so this is a real capacity limit — and it is not the number on the specification sheet. 一顆 VM 磁碟就是一個 LUN，所以這是實實在在的容量限制——而它不是技術規格表上那個數字。

Ask the NAS, not the datasheet. SYNO.Core.System info with type=define reports the model's own ceilings, and neither public reference client reads them. A DS918+ holds half the LUNs the marketing figure suggests. 問 NAS，不要問規格表。SYNO.Core.System 的 info（type=define）會回報機型自己的上限，而兩份公開的參考實作都沒有讀它。一台 DS918+ 只能放行銷數字的一半。

At the ceiling DSM refuses cleanly — 18990541 for LUNs, 18990542 for targets, 18990543 for snapshots. Nothing is damaged, but the refusal reaches an operator as an allocation failure with a five-digit number in it while pvesm status goes on showing terabytes free, because free space is not the problem and adding disks will not fix it. 開到上限時 DSM 會乾淨地拒絕——LUN 是 18990541、target 是 18990542、快照是 18990543。什麼都不會壞，但那個拒絕到操作者眼前是「配置失敗」加一個五位數字，而 pvesm status 還繼續顯示好幾 TB 可用——因為可用空間不是問題所在，加硬碟也解決不了。

So the plugin refuses first, with a message that names the real reason, and warns once while sixteen remain. The count includes LUNs this storage does not own — the owner's own and any Virtual Machine Manager disks consume the same ceiling. That is the second reason it never sends the types filter Synology's own client sends: that filter hides exactly those objects, so a client trusting it would under-count against the ceiling it was checking. 所以 plugin 會先拒絕，用一句說得出真正原因的話，並在剩下十六個時警告一次。這個數量包含不屬於這個 storage 的 LUN——擁有者自己的、以及任何 Virtual Machine Manager 的磁碟，都吃同一個上限。這就是它從不送 Synology 自己那份型態過濾條件的第二個理由：那個過濾條件藏起來的正是這些物件，所以相信它的用戶端會在它正在檢查的那個上限上少算。

The three ceilings in the order they bite: LUNs, one per VM disk; snapshots per LUN, 256 and shared with the user's own SAN Manager schedule; and targets, irrelevant in the default shared mode which uses one — and the reason per-volume is not the default, since 128 targets would cap the storage below the LUN ceiling. 三個上限按會先咬到你的順序：LUN，每顆 VM 磁碟一個；每顆 LUN 的快照，256 個，而且和使用者自己的 SAN Manager 排程共用額度；以及 target，在預設的 shared 模式下無關緊要，因為只用一個——這也正是 per-volume 不是預設的原因，因為 128 個 target 會把 storage 卡在低於 LUN 上限的地方。

syno-portal takes a list, tried in order and rotated on failure. The rotation happens inside the login and the request URL is built after it — a related project shipped a bug where the URL was built first, so every retry went on travelling to the address that had just been found dead. syno-portal 收一份清單，依序嘗試、失敗就輪替。輪替發生在登入裡面，而請求的 URL 是在輪替之後才組——相關專案出過一個缺陷：URL 先組好了，所以每次重試都繼續送往剛剛才被判定死掉的那個位址。

On a UC chassis the second address need not be configured: SYNO.Core.Network.Interface accepts relay_node=node0 and node1 to enumerate the peer controller. On a single-controller NAS both answer with the same interfaces, so the mechanism is harmless where it is not needed — and on UC models a target's network_portals also carries a controller_id, which a single-controller NAS omits entirely. UC 機箱的第二個位址不必手動設定：SYNO.Core.Network.Interface 接受 relay_node=node0 與 node1 來列舉對側控制器。在單控制器的 NAS 上兩者回傳相同的介面，所以這個機制在不需要它的地方是無害的——而 UC 機型上 target 的 network_portals 還會帶 controller_id，單控制器的 NAS 完全不回傳這個欄位。

Neither has been run on hardware, and the plugin says so.兩種都沒有在實機上跑過，而 plugin 會說出這件事。 SHA is low risk — one address that happens to move, which is already handled. UC is a genuine unknown: whether a LUN is owned by one controller, and whether a target's portals differ per controller, together decide whether a node still reaches its disk after a failover. So the plugin warns on DSM UC rather than refusing, and this page keeps saying unverified until someone reports a run. SHA 風險低——就是一個會移動的位址，而那已經處理了。UC 是真正的未知：一顆 LUN 是否由單一控制器擁有、target 的 portal 是否依控制器而不同，這兩件合起來決定故障切換之後節點還找不找得到自己的磁碟。所以 plugin 偵測到 DSM UC 時發出警告而不是拒絕，而這一頁會一直寫著未驗證，直到有人回報實際運行結果。

If you run either, the most useful thing you can report is one number: does SYNO.Core.ISCSI.Node's uuid stay the same across a failover? A storage's identity is pinned to it, so if it changes, that pin stops protecting the storage and starts breaking it. 如果你手上有其中任何一種，最有價值的回報是一個數字：SYNO.Core.ISCSI.Node 的 uuid 在故障切換之後還是同一個嗎？storage 的身分釘在它上面，所以如果它會變，那道釘子就不再保護 storage，而是開始破壞它。

The discovery tool探索工具

This works today. It is read-only and safe against a production NAS. 這個現在就能用。它是唯讀的，對正式機是安全的。

It creates nothing, deletes nothing, and logs out after itself. The password is prompted for with echo off — never passed on the command line, where it would be visible in ps and in the shell history. 它不建立、不刪除任何東西，跑完會自己登出。密碼以關閉回顯的方式提示輸入——絕不從命令列傳入，那會在 ps 和 shell 歷史裡看得到。 

# from a .deb release, or straight out of the repository
pve-syno-api-probe --host 192.0.2.10 --user pve-storage

It reports the API set and every version range the NAS accepts, whether anti-CSRF is on, the DSM volumes and their filesystems, the LUNs and targets as they are now, the dev_attribs of an existing LUN, and a closing register of what the run settled and what still needs a write to answer. 它會回報 NAS 接受的 API 範圍與每一個版本區間、防 CSRF 是否開啟、DSM 儲存空間及其檔案系統、目前的 LUN 與 target、一顆既有 LUN 的 dev_attribs，最後給出一份登記簿：這次跑完解決了什麼、還有什麼需要寫入才能回答。

About --probe-methods關於 --probe-methods

It names a LUN and snapshot uuid the NAS has never issued, so a method that exists can only refuse — and the refusal code proves it is there. DSM answers 103 for a method it does not have, and an object-not-found code for one it does. Nothing it could act on is real, but the names being sent are destructive ones, so it asks first. 它指名一個 NAS 從未發出過的 LUN 與快照 uuid，所以存在的方法只能拒絕——而拒絕的錯誤碼證明它在那裡。DSM 對沒有的方法回 103，對有的方法回「找不到物件」。它能動到的東西並不存在，但送出的畢竟是破壞性方法的名稱，所以先問過再做。

This is how R-1 gets answered, and it is the single most useful thing an owner of a Synology NAS can contribute to this project. R-1 就是這樣回答的，而它是一位 Synology NAS 的擁有者能為這個專案做的最有價值的一件事。

The DSM accountDSM 帳號

Do not give this plugin your admin account. And there is one thing DSM will not let you restrict, which you should know before deciding how to network the NAS: SAN Manager's API has no privilege you can grant for "manage LUNs". There is no SAN operator role, and the per-user Application privileges list does not contain SAN Manager, so the account has to be an administrator. 不要把 admin 帳號給這個 plugin。而且有一件事 DSM 不讓你限制，你應該在決定 NAS 的網路配置之前先知道：SAN Manager 的 API 沒有任何一個可以單獨授予的「管理 LUN」權限。沒有 SAN 操作員角色，每位使用者的「應用程式權限」清單裡也沒有 SAN Manager，所以帳號必須是管理員。

That is a limitation of DSM, not a shortcut taken here. What can still be taken away from the account is everything else — every shared folder, every application except DSM itself, and any address that is not one of your PVE nodes. A leaked credential then cannot be used to browse your files over SMB or Drive, which is the difference between an incident and a disaster. 這是 DSM 的限制，不是這裡便宜行事。仍然可以從那個帳號拿掉的是其他一切——每一個共用資料夾、除 DSM 以外的每一個應用程式，以及任何不屬於你的 PVE 節點的位址。這樣一組洩漏的憑證就無法用來透過 SMB 或 Drive 翻你的檔案，而那是「一次事故」和「一場災難」的差別。

Requirements系統需求

DSM 7.0 or later, and only 7.1.1 verified. Dual-controller DSM UC is refused, not approximated. The version is a floor, not the decision: the capability gates, the advertised API set and a Btrfs volume are what actually decide, and Btrfs support is model-dependent — an entry-level NAS on 7.2 may still be unusable7.0 以上，而且只驗證過 7.1.1。雙控制器的 DSM UC 會被拒絕，不會假裝支援。版本號只是門檻不是判準：真正決定的是能力閘門、公佈的 API 範圍，以及儲存空間是不是 Btrfs——而 Btrfs 支援是看機型的，一台跑 7.2 的入門機仍然可能不能用
Volume儲存空間 Btrfs. Snapshots exist only for a thin LUN on Btrfs, so an ext4 volume is refused when the storage is added rather than failing at the first snapshotBtrfs。快照只存在於 Btrfs 上的精簡 LUN，所以 ext4 的儲存空間在加入 storage 時就被拒絕，而不是等到第一次拍快照才失敗
Model型號 One with iSCSI target support. The LUN ceiling is per-model and the NAS reports it — a DS918+ says 256, not the 512 on the datasheet支援 iSCSI target 的機型。LUN 上限是看機型的，而且 NAS 會回報它——DS918+ 說 256，不是規格表上的 512
Network網路 HTTPS to DSM. Plain HTTP is refused — DSM would accept the login with the password in a URL, and that writes it into the NAS's own access log以 HTTPS 連到 DSM。純 HTTP 一律拒絕——DSM 會接受把密碼放在 URL 裡的登入，而那會把它寫進 NAS 自己的存取記錄
Proxmox VE 8.x / 9.x. The storage API version is negotiated against the node, never hardcoded8.x／9.x。儲存 API 版本是對節點協商出來的，從不寫死

How to help如何協助

The most valuable contribution is a run of the probe against a model or DSM version other than a DS918+ on 7.1.1. Synology's API is not a stable published contract, so a second data point is worth more than any amount of reasoning about the first. 最有價值的貢獻是在不是 DS918+、不是 7.1.1 的機型或 DSM 版本上跑一次探索工具。Synology 的 API 不是一份穩定公開的契約，所以第二個資料點比對第一個做任何推論都有價值。

Particularly wanted: 特別想要的：

  • R-1 — the output of --probe-methods on any DSMR-1——任何 DSM 上 --probe-methods 的輸出
  • A LUN's uuid together with its WWID from a host that has it attached, to test the derivation rule against a second sample一顆 LUN 的 uuid，加上在掛著它的主機上讀到的 WWID，用第二個樣本檢驗那條衍生規則
  • Whether a non-administrator account can reach the SAN APIs at all非管理員帳號到底能不能呼叫 SAN API
  • Anything the probe reports that contradicts this page探索工具回報的任何與本頁矛盾的內容
